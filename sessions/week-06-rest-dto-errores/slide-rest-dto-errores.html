DTO · Entrada/Salida

Separar API del modelo interno

El controller nunca recibe ni retorna la entidad JPA. Usa un DTO de entrada validado (@Valid) y un DTO de salida con solo los campos públicos.

⚠️ Problema: la API expone datos internos que el cliente no necesita y no indica qué dato está mal.
CreateOrderRequest (record)
├─ customerId   @NotBlank
├─ items       @NotEmpty
└─ deliveryAddress @Size(min=10)

OrderResponse (record)
└─ orderId, status, totalAmount...
Errors · Consistencia

Un solo contrato de error

Un @RestControllerAdvice centraliza todos los errores. Cada excepción se traduce a un status HTTP correcto y un mensaje legible — nunca un stack trace.

⚠️ Problema: ante cualquier error, la API responde 500 y expone el stack trace al cliente.
400 → MethodArgumentNotValidException
404 → OrderNotFoundException
500 → Exception genérica (sin trace)
Formato de error — siempre igual
{
  "timestamp": "2026-09-17T10:30:00",
  "status": 400,
  "errors": ["deliveryAddress: mínimo 10 caracteres"]
}
Hoy transformamos OrderController: entra/sale solo DTOs (nunca la entidad) y cada error tiene un formato consistente y sin stack trace.
Buenas prácticas para recordar
URLs consistentesPlural + recurso + verbo HTTP.Ej.: POST /api/orders
DTOs explícitosRequest y response separados.Ej.: OrderResponse no expone la entidad.
Validar en la entradaFallar pronto y explicar qué corregir.Ej.: @NotBlank customerId
HTTP con intenciónUsar 2xx, 4xx y 5xx correctamente.Ej.: creado = 201, no 200.
Sin filtrar detallesLogs internos; respuestas seguras.Ej.: cliente recibe 400, no stack trace.
⚠️ Antes — entidad cruda + 500 genérico

Sin validar · sin DTO · error ilegible para el cliente
✅ Después — DTO + RestControllerAdvice
sequenceDiagram
    participant C as Cliente
    participant OC as OrderController
    participant EH as RestControllerAdvice
          C->>OC: POST /api/orders (CreateOrderRequest) @Valid
          OC-->>C: 201 + OrderResponse (solo campos públicos)
          C->>OC: POST /api/orders (address corta)
          Note right of C: Este es el caso inválido
          OC->>EH: MethodArgumentNotValidException
    EH-->>C: 400 + errores legibles
El segundo request falla: Advice convierte la excepción en 400 + errores legibles
